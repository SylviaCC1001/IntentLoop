# 固定双空间：实现与部署

## 产品规则

- 固定提供「招采需求空间」（`procurement`）和「Cowork需求空间」（`cowork`）。登录和注册均需明确选择空间。
- 每个空间拥有独立的账号、角色、Session、SQLite 数据库、PRD、原型、附件、Git 历史和评审数据。
- 同一邮箱可在两个空间分别注册，密码和角色独立。原有账号仅属于 Cowork，不能直接登录招采空间。
- Cowork 使用 `COWORK_INVITE_CODE`，未配置时兼容原来的 `INVITE_CODE`。招采必须单独配置 `PROCUREMENT_INVITE_CODE`；未配置时禁止注册。没有内置通用邀请码兜底。
- 每个空间首个注册账号为管理者，其后为产品角色。空间负责人应先完成注册；首个管理者分配在数据库事务中串行完成。
- 侧栏显示当前空间；通过「登出 / 切换空间」返回登录页重新选择。一个浏览器会话使用一个空间，不提供同时保持两个空间登录的功能。
- 不包含自助创建空间、统一账号/跨空间成员关系、计费、SSO 或匿名分享。

## 数据隔离与历史迁移

使用一份应用、两套数据库和文件目录；不依赖每条 SQL 增加过滤条件。

| 空间 | 数据库 | 原型、附件、Git 仓库 |
| --- | --- | --- |
| Cowork | 原 `DATABASE_URL`，未设置时为 `DATA_DIR/prd.db` | 原 `DATA_DIR/{prototypes,appendices,repos}` |
| 招采 | `DATA_DIR/tenants/procurement/prd.db` | `DATA_DIR/tenants/procurement/{prototypes,appendices,repos}` |

`DATA_DIR` 未配置时为 `./data`。`DATABASE_URL` 是 SQLite 文件路径。

历史迁移采用原位归属：原数据库和文件全部作为 Cowork 数据保留，不移动、不复制、不重写资源 ID、版本或署名；新增一个空的招采数据库，并在两个库中增加原型预览凭证表。已有仅包含 `prd_session` 的登录 Cookie 继续归属 Cowork。

HTTP 入口从固定白名单解析空间，并在该空间的数据库中验证 Session。更改 `prd_tenant` Cookie 不能把一个空间的 Session 用到另一个空间。业务页、API、成员管理和 Git/文件操作均使用该请求选定的数据库和目录，不修改进程全局环境变量。

原型路由需登录，且文档和版本必须存在于当前数据库。HTML、CSS、JS、图片等文件均受保护。首次访问需正常登录，随后重定向到仅限该会话、空间、文档和版本的随机预览凭证路径，供不携带应用 Cookie 的沙箱子资源使用。凭证有效期 15 分钟，只能读取原型资源，不暴露应用 Session ID；会话过期、登出或文档/版本删除后失效。预览超时后从应用中刷新预览重新授权。注释代理会将凭证路径还原为稳定文档路径，保留历史锚点。

路径检查同时阻止越界和指向空间目录外的符号链接。HTML 响应包含 CSP sandbox，直接打开原型文件时也不会获得应用同源脚本权限；iframe 保留现有沙箱。响应禁止缓存并设置 `Referrer-Policy: no-referrer`。预览凭证 URL 属于短期只读凭证，不应分享或记录到普通访问日志；部署时应在反向代理中屏蔽或脱敏 `/proto/~/` 的凭证路径。

预览在原型脚本运行前检测 `localStorage` 和 `sessionStorage`。浏览器禁止访问时，为当前预览窗口提供临时内存存储，支持 `getItem`、`setItem`、`removeItem`、`clear`、`key` 和 `length`；两个存储独立，不与其他预览或应用共享数据。刷新或关闭预览后清空，不保证浏览器存储的持久化与跨窗口同步行为。已有可用存储保持不变。兼容脚本仅在展示时注入，不改写上传文件；批注导出时移除。

## 本地验证

使用 Node 22。不要把生产 `DATABASE_URL` 或生产 `DATA_DIR` 传给测试。

```bash
npm run lint
npx tsc --noEmit
npm run build
npm run test:smoke
npm run test:tenants
```

`test:tenants` 要求先完成生产构建。它自行创建临时数据库、文件和 HTTP 服务，运行后停止服务并删除临时数据。覆盖旧库原位迁移和重复迁移、旧 Session、独立注册邀请码、同邮箱独立账号、登录选择、篡改空间 Cookie、双向 API/页面/文件访问隔离、原型静态资源、CSP 响应头、无 Cookie 的受限原型资源授权、凭证过期和登出撤销、并发请求、Git 目录和登出隔离。

另需在隔离的本地或 staging 服务上运行 `npm run test:pages`，使 `SMOKE_BASE_URL`、`DATABASE_URL`、`DATA_DIR` 指向同一测试环境。

## 发布前准备

本文件只描述发布步骤，不代表已经修改远端环境。

1. 重新核对生产代码提交、systemd 工作目录、环境文件、实际 `DATABASE_URL` 和 `DATA_DIR`。历史环境为 `/opt/intent-loop/app` 与 `/opt/intent-loop/data`，不得直接假定仍一致。
2. 在环境文件中配置独立的 `PROCUREMENT_INVITE_CODE`，保留原 Cowork 邀请码。不要将生产邀请码提交到 Git、写入日志或发给其他空间成员。
3. 先在隔离 staging 环境运行迁移、构建和测试，用合成数据验证两个空间。现有 `deploy-staging.sh` 会刷新 Cowork 的生产数据库与附件快照；它不是空白测试环境初始化脚本，不应直接用于外部试用。
4. 如果使用旧 staging 脚本的生产快照功能，务必先停 staging 服务，确认 staging 的 `DATABASE_URL` 与 `DATA_DIR`，并限制访问。脚本只刷新 Cowork 快照，招采目录由双空间迁移初始化或保留，绝不能让 staging 指向生产招采目录。

## 正式部署

1. 确认维护窗口，暂停业务写入。
2. 备份实际 SQLite 数据库及完整文件树。已经使用招采空间后，备份必须包括 `DATA_DIR/tenants/procurement`，不能仅备份原来的 `prd.db`。SQLite 应使用一致性备份或停服务后完整备份，不要只复制正在写入的 `.db` 文件。
3. 激活正确生产环境变量后运行 `npm run db:migrate`，日志应列出两个空间和各自的数据库路径。禁止在错误工作目录下用默认配置迁移。
4. 构建并发布应用；沿用现有受控发布流程，确认服务工作目录、运行账号及数据目录权限。
5. 先验证原 Cowork 账号、历史方案、版本、评审、原型和附件，再由招采负责人使用专属邀请码注册首个管理者。
6. 验证招采初始为空；分别创建测试方案，检查双方列表、详情、下载、原型和成员管理互不可访问；删除自己创建的验证内容。
7. 分别确认部署提交、systemd 状态、应用端口、Nginx 入口及实际外部访问地址。检查 HTTPS 与生产 Cookie Secure 配置，不要把测试用 `COOKIE_SECURE=false` 沿用到 HTTPS 生产环境。

## 回滚

此版本不向原业务表增加租户列，也不移动原文件。回滚旧应用后，Cowork 仍使用原数据库；招采数据保留在独立目录，但旧应用不能访问它。不要删除招采目录，也不要用空库覆盖它。

如需恢复数据备份，先停服务并明确备份时间之后的数据如何保留；不得直接覆盖已经产生新业务数据的数据库或文件。应用回滚与数据恢复是两个独立操作。
